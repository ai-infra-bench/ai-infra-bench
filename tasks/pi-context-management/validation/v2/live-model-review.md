# v2 真实模型行为试跑

新版扩展能被真实模型使用。GPT-6 Astra 完成整条流程；GPT-5.6 Sol 出现多余切换，最终自行完成第一阶段，并在人工中断后的第二阶段恢复中完成证据核验。不能把后者记为未经干预的一次完整通过。

这是模型使用参考实现的测试，不是模型解编程题的 solver pilot。模型输出真实，实验快照为合成数据。运行本地 Pi 源码；本轮没有重复 Docker 评测。工具接口、题面及参考实现保持冻结版本不变。

## 场景与执行

第一阶段比较 A/B/C 三组超时配置，阈值 error_rate <= 0.005、p95_ms <= 500，选择唯一达标的 B。每读一组，模型自己写工作笔记并调用 new_context。笔记保留来源线索，不抄原始审计字段。随后正常重启同一 session，要求找回 B 的三个随机审计字段并提交报告。

工具调用顺序、参数、笔记、搜索词、读取记录和报告全部由上游真实模型生成。观察器只提供数据、收集事件及报告。独立核对网关捕获证明：Pi 输入完整转发，实际工具名与参数逐项匹配上游完成响应；两条完成路径最后一条助手消息均为 stop，而非只依赖进程退出码。

| --- | --- | --- |
| reasoning effort | high | high |
| 独立场景 | 1 次 | 1 次，第二阶段有人工中断恢复 |
| 实际模型请求 | 18 | 原始阶段一 33，恢复阶段二 8 |
| new_context 调用 | 3 | 11 |

两者自己在笔记里保留了 `bulk-B-0000` 作为检索线索，第二阶段自己用这个词调用 history_search，并读取返回的真实 window_id/item_id。搜索词没有由测试脚本在切换后注入。

## 发现：笔记保留了已执行动作的待办表述

GPT-5.6 在处理 C 后的笔记里写着：

> C 后工作笔记已保存，下一步调用 new_context，然后给出简短结论。

切换会删除原助手调用和工具结果，笔记却仍保留这句待办。模型随后反复读/写笔记、调用 new_context。C 后实际切换 9 次，总计 11 次，比任务需要多 8 次，最终自行给出结论。

这是实际的重复动作，不是 HTTP 重试：每次都能在上游生成的工具调用和 Pi 工具完成事件中对应。笔记的待办措辞与切换完成信息不足是值得验证的解释；本轮未做单变量对照，不能断言唯一根因。

确定性测试始终由脚本指定下一步，因而不会暴露这种决策问题。可在后续对照中验证：新窗口明确携带“本次切换已完成”的状态，能否减少重复动作。当前未修改扩展或给模型追加纠错提示。

## 人工中断与恢复

观察到 GPT-5.6 在 C 后多次切换时，操作方决定提前停止以避免空转。但在定位进程并执行停止的期间，模型已经自行完成第一阶段。信号实际终止了刚启动的第二阶段进程，退出码 -15。

第二阶段未产生任何观察事件，也未写入第二阶段用户消息或完成任何工具调用。因此保存原始失败运行和停止记录后，恢复使用完整、字节相同的第一阶段 session 检查点，继续原第二阶段提示；没有丢弃模型已执行的第二阶段动作，也没有修改模型、提示或工具。恢复结果单列，不作为新的独立尝试。见 `gpt-5.6-sol-resumed/recovery.json`。

第一次恢复准备因未找到第二阶段用户边界而安全退出，未发模型请求；核对第二阶段尚未初始化后，改用完整第一阶段文件继续。

## 限流与边界

GPT-6 的网关记录了 6 次 HTTP 429，最终退避成功。GPT-5.6 原始阶段一有 6 个请求、恢复阶段二有 4 个请求在 HTTP 200 后的响应流中返回限流错误，Pi 重试后完成。请求数包含这些失败请求；流内 error 与 response.failed 可能属于同一请求，不重复计数。

保留目标、系统指令和笔记，旧原始日志退出上下文，历史原文恢复，session 和工作区保持，已由实际请求及最终字段核验。这里明确要求切换，不证明模型会自主选择合适时机；单样本也不足以估计稳定成功率。

复跑说明见 README.md；代码为 run.py/provider.ts；可见轨迹为各模型的 trace.md；原始请求、模型响应及事件保留在 capture/ 与 events.jsonl。可见轨迹不展示内部推理。网络与完成性复核见 network-and-completion-audit.json，冻结输入完整性见 integrity.json。
