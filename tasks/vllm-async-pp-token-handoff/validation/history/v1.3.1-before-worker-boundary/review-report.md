# Async PP task review

The task can be retained after repairing the scheduler boundary. Version 1.3.1 leaves the statement and environment unchanged and removes a demonstrated verifier incompatibility. The captured Astra submission received reward 0 when a fixture omitted candidate-added scheduler metadata, then reward 1 through the repaired full entrypoint without changing the submitted code. The final 16-case matrix matches every expected reward, and the final Harbor Oracle passes with reward 1 and no exception. The task can be retained with this repair.

## Task contract

The task is a realistic request to extend the frozen vLLM mp backend to async PP=2 with ordinary decoding, chunked prefill and correct request/output lifecycles. The user approved the final English statement. It specifies externally observable requirements and does not prescribe Oracle helpers, maps, sentinels or a PP wire layout. The synchronous and PP=1 regressions follow directly from its final sentence. Historical PRs inform regressions; the task does not claim to reproduce one historical PR exactly.

## Environment

The target boundary is request admission -> production scheduler -> mp executor and worker processes -> runner, NCCL handoff and subsequent model input -> collected output and request completion. The pinned image and environment recipe are unchanged. The image supplies the Base source and CUDA/NCCL dependencies; task tests, controls and the reference patch remain verifier-only. The task declares a 10-hour agent budget, no network and two A100s. The separately requested model trials use host networking and a proxy; their trajectories are not evidence of cutoff-isolated solving. The validation controls and rescore replay use isolated containers. The small OPT weights are generated by the verifier from the installed architecture, so validation needs no model download.

Component cases now run request admission and the scheduler selected by the candidate configuration, passing each complete production scheduling result directly to the runner. Model arithmetic is deterministic, while buffers, scheduling, sampling, input preparation and NCCL remain real. Fully collected warmup creates generated history, and natural request completion drives compaction and empty rounds. The real-model tests additionally execute attention, KV cache and the normal mp worker path. In the async PP=2 case the frontend is in-process so the stable executor submission boundary can be observed; both model workers remain independent processes. A task-owned RPC temporarily holds worker progress and is released only after the same request has another submitted step. This preserves the delayed-output condition without a throughput threshold or a prescribed queue representation.

## Verification changes

The full bidirectional contract-to-case map is in semantic-boundary.md. The verifier now exercises overlapping scheduling and output closure, mixed prefill/decode, removal and compaction, reorderings, discarded-token progress, empty execution, synchronous behavior, PP=1 and fresh admission after draining. Actual model forward arguments are captured and compared by request identity. The fixture no longer infers scheduler events from placeholder lengths or invokes one candidate-added input/sampling helper.

Both production PP endpoints load the candidate. A separate root-owned GPU observer supplies fresh sampler inputs and checks downstream GPU inputs using separate observation groups. The candidate can choose broadcast or P2P and its own tensor representation. Correct controls exercise reversed storage and P2P with renamed internal helpers. The root scorer also requires complete worker reports and successful external GPU comparison.

CUDA observation includes explicit and implicit runtime waits. An event recorded before sampling can guard existing input-buffer reuse; the exemption ends if that event is recorded again. This is based on temporal provenance, not an event attribute name. Expected E2E output and partial comparison files are root-only, and candidate scratch outputs are removed between configurations.

## Reproduced findings

The Astra trial rruzoCB exposed an additional P1 verifier defect after the 1.3.0 control matrix: worker_fixtures and lifecycle_cases built SimpleNamespace scheduler outputs instead of running the upstream producer. The submitted SchedulerOutput added sampled_token_positions, populated by AsyncScheduler before returning a scheduled step. Both GPU ranks crashed on the missing fixture attribute before checking tokens. The replacement admits real requests, retains candidate metadata and exercises actual scheduler-to-runner transitions on both ranks. It does not add a special case for that field. The unchanged original submission passes the repaired full entrypoint, and its production diff is retained as a scheduler-metadata alternative. Original failing logs and the diagnosis are archived separately; the raw reward is not rewritten.

During revalidation, a prompt-corruption assertion could leave the other test rank entering another output-collection collective. The component case now agrees on assertion failures before entering another cycle. The token-loss control is rejected with a concrete next-input mismatch, rather than waiting for that test-side disagreement to time out.

The historical Oracle misses the all-prefill progress, compaction prompt-preservation and last-rank idle guards. The reference patch now contains the three scoped repairs, with each repair separately removable as a negative control. The independent peer initially prescribed a PP protocol, and input checks initially prescribed a helper/buffer; these assumptions were replaced with behavioral boundaries.

The report-only negative originally had incomplete framing after suite merging. It was repaired and rerun: structurally valid reports still receive zero because the independent GPU comparison fails. A copied-reference negative reaches the expected-output read and receives PermissionError in the pre-overlap verifier, establishing the permission fix independently of later overlap instrumentation. In the final verifier its fake LLM also lacks the real mp executor required by the async probe; the other three configurations still reach the protected reference read and fail with PermissionError.

A serial executor that waits for every submitted execute/sample result received reward 1 through the optimized-v4 full grading entrypoint. Its token outputs remain correct. The new delayed-output probe accepts the Oracle and P2P alternative and rejects this serial executor specifically because the next request step is not submitted before prior work is released. The frozen latest-source grading entrypoint now assigns that serial executor reward 0.

## Validation and limits

The original 1.3.0 results are retained under history/v1.3.0-before-scheduler-boundary and do not certify the new fixture. The frozen scheduler-boundary-release snapshot passes all 16 controls: four correct implementations receive 1 and twelve incomplete or faulty implementations receive 0. The Oracle also passes the final Harbor trial task__qnAEteB with zero exceptions. Harbor 0.22.0 uses the local NvidiaDockerEnvironment adapter solely to allocate two GPUs because the stock Docker backend does not allocate them. Task scoring is unchanged by that adapter. Rewards, elapsed times, raw logs and executable hashes are recorded in e2e-evidence.json and local-regressions.json. The direct Oracle run took 454.7 seconds; the Harbor verifier took 468.58 seconds. Correct alternatives took 471.3–478.8 seconds under shared GPU load. Base and duplicate-collection controls already fail their CPU behavioral checks; their subsequent GPU setup exceptions are secondary diagnostics, not the evidence used to justify rejection.

These tests cover representative cases implied by the contract, not an exhaustive state space. Worker-side Python instrumentation is not a general security boundary against arbitrary candidate tampering. The observed report-only, early-exit, reference-copy and serial-execution controls provide specific evidence; they do not establish universal tamper resistance. No claim is made that a full model rollout trajectory was reviewed in this hardening pass.

Validation was performed in the dedicated task worktree before the user authorized publication to codex/async-pp-behavior-hardening. Only this task directory is included; the main workspace and unrelated tasks are untouched.
