# Runtime payload growth and profiling coverage — 1.4.1

The public contract now requires fixed encoder output to retain bounded embedding payload storage as non-embedding prompt positions increase. It also preserves profiling coverage of the storage the implementation actually retains. A dense representation that profiles its larger storage correctly satisfied 1.3.4; the additional storage requirement makes that historical control a negative in 1.4.0.

Version 1.4.1 keeps this contract. Template-only factories do not transmit embedding values, so a metadata allocation made with `output.new_empty` is no longer counted differently from `torch.empty`. Later copies of actual encoder values into either allocation are still tracked. The observer therefore distinguishes value propagation from the choice of allocation syntax.

The scored producer emits eight rows of sixteen float32 values. Three valid prompt spans contain 16, 128 and 4096 positions, with the same output rows and a consistent token-derived embedding mask. Requests enter real scheduler and runner constructors, admission, execution, cache write and model input merge. The cache is inspected while the request still needs later embeddings, before normal completion can release it. No private cache container or helper is used for the observation.

A Torch dispatcher observer tracks encoder-derived storage through aliases, copies and in-place scatter. Weak C++ storage handles allow raw-storage ownership and views without keeping allocations alive. A pool allocated in the runner constructor is counted once encoder data reaches it. Input masks and index computations are not tainted as embedding payload. Constant decoder input buffers may become tainted too; their size is fixed across the compared spans. The growth check allows bounded overhead and compares growth rather than a required exact byte count.

For the same maximal media input, a second normally constructed runner executes real `profile_run`, media production, encoding and decoder dummy execution. At the actual model forward boundary the observer compares resident initialization plus retained payload against the runtime path. Initialization is included on both sides so preallocation and ordinary decoder buffers do not create an exclusion loophole or double counting. Conservative profiling is permitted.

Regressions exercise alias counting, storage retained after a Tensor wrapper is deleted, in-place scatter, preallocated buffers and actual release. Full controls include transposed and sparse compact representations, ordinary dense storage, and a dense pool reserved during construction. Sparse values and index storages are observed separately so a legal sparse layout is not rejected for lacking a single contiguous storage object. The final matrix records their actual rewards and failure reasons. These are CPU tensor storage observations, not CUDA allocator peak measurements or claims about arbitrary Python/native payload encodings.

A second scored workload now observes residency across completed-request turnover in one live scheduler/runner pair. Each request uses the full eight-row encoder capacity and needs that item across several prefill chunks. All model inputs are checked as execution advances. Twenty-four distinct media requests force capacity reuse; observations after four warmup requests distinguish bounded retained pools from continuous accumulation. Scoring inspects weak backing-storage observations, not a cache dictionary, an eviction callback, a particular tensor address or the lifetime of one chosen wrapper. A reusable-buffer implementation is a positive control. Keeping evicted tensors or their copies elsewhere is a negative even though scheduling and output values remain correct.
