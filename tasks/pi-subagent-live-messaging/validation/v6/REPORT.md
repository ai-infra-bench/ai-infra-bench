# Pi 子 agent 实时通信：pass@4

本题 G6 和 G56 各有四份独立提交。两种模型都在四次内至少成功一次，单题 pass@4 均为 1。

| 模型 | 第 1 次 | 第 2 次 | 第 3 次 | 第 4 次 | 成功次数 | 单题 pass@4 |
|---|---|---|---|---|---|---|
| G6 | 18/18 | 18/18 | 18/18 | 18/18 | 4/4 | 1 |
| G56 | 17/18 | 17/18 | 18/18 | 18/18 | 2/4 | 1 |

每份提交必须全部通过 18 项行为测试才算成功。四次包含之前已完成的一次和本次新增的三次；之前的提交也使用同一版评分器重新评分。没有改写模型提交，也没有将评分结果反馈给求解模型。

## 测的是什么

真实模型负责实现功能。评分时启动真实 Pi 主进程和子进程，用确定性脚本扮演模型，观察消息是否进入接收方下一次实际模型请求，是否按序、仅一次、带发送者身份送达，以及隔离、结束边界和取消行为。`use_finding` 还要求 B 使用 A 发来的随机 API 路径完成真实工具请求。评分脚本本身不请求在线模型。

因此这里衡量的是“模型写出的实现能否通过这些行为场景”，不是“真实模型之间自由协作的任务成功率”。

## 失败项

- g56-1：`ordered`；两条消息都已接受，但 B 下一次请求只含第一条，第二条晚一轮出现。
- g56-2：`ordered`；两条消息都已接受，但 B 下一次请求只含第一条，第二条晚一轮出现。

## 本轮修正了评分器的三处假设

1. 旧测试假定第五个 worker 必须排队，但题面没有规定开启通信时的并发上限。改为五个 worker 的私信隔离场景，同时接受分批启动和同时启动。
2. 旧观察器只从进程参数识别任务，会错判通过 RPC stdin 接收任务的合法实现。现在从实际任务 prompt 识别身份，去掉必须带 `Task:` 前缀的限制。用未修改 Base 的独立 RPC 探针复现并验证了修复。

3. 队友发现先确认参与通信的进程已经运行，再要求能发现它们；允许只返回运行中队友的实现省略排队或已结束的成员。

全部正式结果统一使用 0.0.6。Oracle 和不同公开接口的 JSONL 正确对照都是 18/18；Base 是 3/18；丢消息、重复消息、反转顺序三个错误对照分别被拒绝。旧版结果和错误对照保留在 artifacts，不混入统计。G6 第 3 次曾因适配器漏识别显式错误结果误记一项失败；补全格式映射后，用同一补丁重新评分为 18/18，没有增加求解次数。

## 可比性与边界

- 两种模型均通过 Codex 0.118.0 / high 求解，使用相同题面、Pi Base 和资源限制；新六份提交各自从干净环境开始。
- 发生限流时按退避策略恢复同一个原生会话，保留已有工作，不作为新的一次抽样。会话 ID、恢复次数和补丁哈希见 `solver-audits.json`。
- 轻接口题允许工具名、参数和返回格式不同；本轮逐份审查并编写评分端适配器，仅转换调用与结果，不实现投递、不改收件人上下文。适配器见本目录各模型编号文件。
- 这是单题四次样本，不能据此判断两种模型在整个 benchmark 上的总体 pass@4 或稳定排名。
- 当前有确定性行为覆盖；完整独立发布审核仍未完成。本次没有提交或推送 Git。
