## 核心测试真正观察到了什么

A 的调查工具获得一个随机 API 路径，B 此时正在执行自己的工具。

1. A 发送消息，得到接受结果。
2. B 的工具正常结束，没有被通信打断。
3. B 的下一次实际模型请求中出现了 A 的完整发现。
4. 测试从这份真实输入中提取路径，让 B 的工具调用接口，返回 200。

B 最初的输入没有这个路径，准备工具的返回值也没提供路径。主 agent 只启动任务并收集最终结果，没有中途替它们转述消息。[独立核对记录](use-finding-audit.json)保存了这个先后顺序。

这里的模型回复由脚本提供，Pi 的子进程、消息传输、工具和上下文注入都是真实执行。因此它验证通信机制，不是“真实模型会不会主动合作”的策略测试。

## 轻接口是否保住了

G6 选择 `communication: true`，用 `team_send({to, text})` 发送，`to: "*"` 表示广播。它采用内存 broker 和 Node IPC，与参考解的文件收件箱不同。

测试只把参数与广播方式映射到这些公开接口，没有替它发送、读取队列或注入消息。[适配器审查](g6-binding-review.md)记录了映射依据。

另一份正确对照还改了工具名称、开关名称和返回字段，同样通过。这说明当前检查能接受这些差异。任意新接口仍需审查者编写适配器，尚未实现完全自动接入所有设计。
